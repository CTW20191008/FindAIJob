# RAG 系统设计文档（定稿）

| 项 | 说明 |
|----|------|
| 文档目的 | 定义一套可落地、可评测、可演进的 **检索增强生成（RAG）** 系统，用于面试陈述、个人项目或团队对齐 |
| 读者 | 应用侧工程师、算法工程师、面试官 |
| 范围 | 企业知识库 / 文档问答类场景；不含纯「仅依赖模型记忆」的闲聊 |

---

## 1. 背景与建设目标

### 1.1 为什么用 RAG

- **知识时效与私有域**：模型参数内知识不可控、更新贵；业务文档可直接入库检索。  
- **可追溯**：答案可绑定引用片段，便于审计与纠错。  
- **幻觉可控**：用「约束只依据上下文」+ 引用 + 拒答策略，比纯生成更可控（不保证为零幻觉）。  

### 1.2 建设目标（可写入 OKR）

- **效果**：给定评测集，检索召回与答案忠实度达到约定水位（见 §8）。  
- **体验**：P99 延迟、首 token 延迟在预算内（见 §10）。  
- **成本**：单次问答 token 与向量调用可估算、可归因（见 §10）。  
- **运维**：可查日志、可复现单次问答链路、支持灰度与回滚（见 §9）。  

---

## 2. 需求说明

### 2.1 功能需求

| ID | 需求 | 说明 |
|----|------|------|
| F1 | 文档接入 | 支持常见格式（txt/md/pdf/html/办公文档等，按实现分期） |
| F2 | 增量更新 | 单篇更新、批量重索引、删除与幂等 |
| F3 | 问答 | 多轮对话可选；首轮以「单轮 RAG」为 MVP 基线 |
| F4 | 引用 | 输出中标明来源（文档 ID、段落/页码/chunk ID） |
| F5 | 拒答 | 检索不足或上下文不支持时明确拒答，不编造 |

### 2.2 非功能需求

| ID | 类别 | 典型指标（按业务取值） |
|----|------|------------------------|
| N1 | 可用性 | 检索与生成服务降级策略明确 |
| N2 | 延迟 | 如：端到端 P99 在数秒量级（依模型与并发约定） |
| N3 | 安全 | 租户隔离、敏感内容过滤、审计日志 |
| N4 | 可扩展 | 文档量、向量维度、QPS 可水平扩展索引与推理 |

## 3. 总体架构

### 3.1 逻辑分层

```
┌─────────────────────────────────────────────────────────┐
│                      接入层（API / Web）                    │
└───────────────────────────┬─────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│  查询理解      │   │   检索服务     │   │   生成服务     │
│  Rewrite/扩写  │   │ Hybrid+ANN     │   │ Prompt+LLM    │
│  多查询可选    │   │ Rerank         │   │ 引用/拒答策略  │
└───────┬───────┘   └───────┬───────┘   └───────┬───────┘
        │                   │                   │
        └───────────────────┼───────────────────┘
                            ▼
                  ┌─────────────────┐
                  │  观测与评估      │
                  │  日志/指标/评测集 │
                  └─────────────────┘

┌─────────────────────────────────────────────────────────┐
│                   离线索引流水线（异步）                    │
│  解析 → 清洗 → 切块 → Embedding → 入库 → 版本发布         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 核心数据流（在线）

1. 用户 **Query** 进入 **查询理解**（可选：规范化、多查询扩展、指代消解）。  
2. **检索**：向量化 + **混合召回**（Dense + BM25 等）→ **Rerank** → 取 Top-N **chunk**。  
3. **上下文组装**：去重、长度裁剪、结构拼 prompt（系统/用户/上下文分离）。  
4. **LLM 生成**：带「仅依据上下文、列引用、不知则拒答」等约束。  
5. **后处理**：引用校验、敏感过滤、可选事实校验（规则/工具）。  

### 3.3 与 Agent 的关系

RAG 可作为 **Agent 的一个 Tool**（`knowledge_search`）：Agent 负责规划与多步工具编排，RAG 负责返回带引用的证据片段。

## 4. 离线索引流水线

### 4.1 文档解析

- **目标**：稳定产出 **纯文本 + 结构信息**（标题层级、表格位置、页码）。  
- **实践**：PDF 注意版式乱序；复杂表格考虑 HTML/Markdown 中间表示；代码与配置单独策略。  

### 4.2 清洗与规范化

- 去重（文档级、段落级）、去噪（页眉页脚、重复模板）。  
- 统一编码、全半角、空白；可选 PII 脱敏（按合规要求）。  

### 4.3 切块（Chunking）

| 策略 | 适用 | 风险 |
|------|------|------|
| 固定长度 + overlap | MVP 快 | 切断语义 |
| 按标题/段落递归切 | 文档知识库主路径 | 超长段需二次切 |
| 语义边界切 | 长文多主题 | 成本高 |

**推荐默认**：**递归切分**（标题 → 段 → 句 → token）+ **overlap（如 10%～20% chunk 长度）**。  

**元数据（必带）**：`doc_id`、`chunk_id`、`source_uri`、`title_path`、`position`（页码/序号）、`version`、`acl`（租户/权限）。  

### 4.4 版本与回滚

- 索引以 **版本号** 发布；在线查询指向 **当前读版本**；写入双缓冲或蓝绿切换。  
- 支持按 `doc_id` 局部重跑，避免全量重建。  

---

## 5. 向量与索引

### 5.1 Embedding 模型选型

- **维度**：与向量库、延迟、精度权衡。  
- **语言与领域**：中文/多语言；法律、医疗、代码等考虑领域模型或微调。  
- **输入长度**：chunk 长度与模型 max length 对齐，超长需截断或二次摘要（慎用摘要链，易丢条件）。  

### 5.2 向量存储与 ANN

- 百万级以上规模优先 **ANN**（HNSW、IVF+PQ 等）；关注 **召回率 vs 延迟**。  
- **过滤**：按 `acl`、`doc_type`、时间范围做预过滤，再 ANN。  

### 5.3 混合检索（强烈建议）

- **Dense**：语义近邻。  
- **Sparse（BM25 等）**：专有名词、型号、条款编号。  
- **融合**：线性加权、RRF（Reciprocal Rank Fusion）等；以离线评测选参。  

---

## 6. 在线检索与上下文组装

### 6.1 查询侧

- **Query Rewrite**：补全省略主语、展开代词（多轮场景）。  
- **HyDE（可选）**：生成假设答案再检索——提召回但可能引入偏题，需 A/B。  
- **多查询**：一题多路检索做并集，再统一 rerank（成本上升）。  

### 6.2 召回 → 重排

- **两阶段**：ANN/BM25 召回 **多**（如 Top 50）→ **Cross-Encoder / 小模型 / LLM** 精排到 Top 5～10。  
- **去冗余**：MMR 或规则合并相邻重复 chunk。  

### 6.3 上下文压缩

- 超长时：**按 rerank 分数截取**；同文档相邻 chunk **合并**；表格整表保留优先于散文截断。  

---

## 7. 生成层（Prompt 与策略）

### 7.1 系统提示要点（示例方向，非唯一文案）

- 仅使用「提供的上下文」作答；上下文不足则 **明确拒答**。  
- 输出中 **引用** chunk 编号或标题路径。  
- 禁止编造内部条款、数字、截止日期；必要时回答「上下文未提及」。  

### 7.2 上下文格式

推荐结构化包裹，便于模型解析与日志对齐：

```
[CONTEXT id=chunk_xxx doc=...]
...片段正文...
[/CONTEXT]
```

### 7.3 后处理

- **引用一致性检查**：生成中声称的条款号是否出现在上下文（规则 + 抽样 LLM 裁判）。  
- **空检索短路**：无合格 chunk 时不调用大模型或走短模板拒答，省成本。  

---

## 8. 评测体系

### 8.1 分层指标

| 层级 | 指标 | 含义 |
|------|------|------|
| 检索 | Recall@k、MRR、nDCG | 相关文档/chunk 是否被召回到前 k |
| 重排 | 精排后 Recall@n | 送给 LLM 的上下文是否足够 |
| 生成 | 忠实度（faithfulness）、引用正确率 | 答案是否被上下文支持 |
| 端到端 | 任务准确率、人工满意度 | 业务问题是否「答对」 |
| 系统 | P50/P99 延迟、单次成本 | 体验与商业化 |

### 8.2 数据集构建

- **真实日志脱敏抽样** + **人工标注**（相关 chunk、是否可答）。  
- **对抗集**：否定句、数值陷阱、跨段落条件、易混淆专有名词。  

### 8.3 回归与发布门禁

- 索引/模型/ prompt 变更必须跑 **固定评测集**；指标下滑超阈值则阻断发布或自动回滚读版本。  

---

## 9. 可观测性与运维

- **Trace ID**：贯穿 query → 检索候选 → rerank 分数 → prompt → 输出。  
- **日志**：检索 Top-k 列表、最终入模 chunk、模型版本、token 用量。  
- **看板**：QPS、错误率、空检索率、拒答率、平均 chunk 数、P99。  
- **Bad case 回流**：标注「检索错 / 重排错 / 模型胡编 / 切块坏」→ 回流改 chunk、embedding、或加同义词表。  

---

## 10. 成本、性能与容量

- **粗算**：`Cost ≈ Embed(query+chunks) + Rerank + LLM(prompt tokens + output tokens)`；重试与多查询倍增。  
- **缓存**：同一 query / 近似 query 的检索结果短时缓存；embedding 缓存。  
- **限流**：按租户与用户；大查询拆批异步（如报告类）。  

---

## 11. 安全与合规

- **权限**：检索与回答均受 **ACL** 约束，避免跨租户泄漏。  
- **注入**：用户内容放入明确槽位；工具与内部提示隔离。  
- **敏感输出**：正则 + 分类器 + 人工审核队列（金融、医疗等场景）。  
- **审计**：谁、何时、问了什么、用了哪些 chunk（合规留痕）。  

---

## 12. 降级与故障处理

| 场景 | 策略 |
|------|------|
| 向量库超时 | 退化为 BM25；再不行模板拒答 |
| Rerank 不可用 | 跳过精排，缩小 Top-k 入模 |
| LLM 限流 | 排队/换小模型/缩短上下文 |
| 索引不一致 | 只读旧版本；禁止写扩散 |

---

## 13. 实施路线（建议）

| 阶段 | 内容 |
|------|------|
| MVP | 单格式文档、递归 chunk、Dense 检索、基础 prompt、引用、简单评测集 |
| v1 | Hybrid 检索、Cross-Encoder 重排、版本化索引、基础看板 |
| v1.5 | 多轮指代、查询改写、ACL、成本优化与缓存 |
| v2 | Agent 编排、自动评测流水线、对抗集与门禁 |

## 14. 面试口述版（约 90 秒）

「整体是 **离线建索引 + 在线检索生成** 两条线。离线把文档解析清洗后 **递归切块**，带上 **doc 与段落元数据**，用 **embedding** 写入向量库，并做好 **版本发布和回滚**。在线侧用户问题先做可选的 **query 理解**，然后用 **向量 + BM25 混合召回** 解决纯语义检索对专有名词弱的问题；召回几十条后用 **cross-encoder 或轻量模型重排**，选出少量高相关 chunk **拼进带引用约束的 prompt** 调 LLM。效果上分层看 **检索 Recall、重排后是否覆盖答案、生成忠实度**，系统上看 **P99 和 token 成本**。工程上必须有 **trace、空检索短路、权限隔离和降级**，否则一上量就会不可控。」
